## Dar teslim kapsamı

### 1. İleri DB migration

- Süreli, tek kullanımlı invitation yaşam döngüsü.
- Membership için güvenli `role` / `active` değişimi.
- İsteğe bağlı StaffProfile ↔ Membership bağlantısı.
- Beş dar mali izin kaydı: tahsilat, fiyat/iskonto/iade düzeltmesi, mali rapor, stok yazımı, masraf yazımı.
- Mali izni yalnız owner verir/geri alır; grant/revoke audit izi tutulur.
- Son aktif owner'ı eşzamanlı iki işlemle dahi kaybettirmeyen DB guard.
- S08 sonrası yeni nesnelerde explicit object grant + RLS/policy ayrımı; owner/BYPASSRLS tenant kanıtı sayılmaz.

### 2. Server-side ekip modülü

Dar `worker/team.ts` yüzeyi:

- ekip görünümü,
- invite create / accept / revoke,
- membership role / active update,
- StaffProfile link / unlink,
- financial permission read / grant / revoke.

Invite accept, authenticated fakat henüz ilgili Business üyesi olmayan doğru e-posta hesabını desteklemelidir. Client business ID/cookie tek başına yetki değildir; S01/S02 session authority, güncel Membership ve Origin/CSRF sınırı korunur.

### 3. Team UI

- Membership hesabı ile operasyon StaffProfile kaydı görsel olarak ayrılır.
- Linked / unlinked durumu açıktır.
- Owner / manager / staff yapabilecekleri kullanıcıya anlaşılır gösterilir; güvenlik yalnız buton gizlemeye bırakılmaz, backend fail-closed kalır.
- Henüz olmayan F14/F15 mali işlemleri çalışıyormuş gibi gösterilmez; yalnız izin kaydı yönetilir.

### 4. SQL / HTTP / UI kabulü

Zorunlu negatifler:

- yanlış e-posta,
- yanlış Business,
- expired / revoked / replay invitation,
- staff self-escalation veya başka üyeye manager/owner verme,
- manager'ın owner-only mali izin dağıtması,
- cross-Business membership / staff link / permission erişimi,
- pasifleştirilen üyenin açık session ile sonraki istekte erişmesi,
- owner düşürme/pasifleştirme yarışında son aktif owner'ın kaybı,
- yeni nesnelerde anon/authenticated accidental object grant.

Clean migration zinciri ve upgrade zinciri mevcut PG17 planında kanıtlanır. Task-graph/CI mevcut S06 required gate'ini kullanır.

### 5. Gerçek staging kabulü

Exact-head deploy üzerinde iki mevcut Auth fixture hesabıyla:

`owner invite -> ikinci hesap accept -> rol/aktiflik değişimi -> izin grant/revoke -> pasifleştirme -> güncel session reddi -> cleanup`

Ayrıca yanlış hesap / replay / revoke negatifleri doğrulanır. Gerçek secret/parola/token Git veya Issue #65'e yazılmaz. Cleanup zorunludur.

## Güvenlik değişmezleri

- Invitation token plaintext DB/Git/log içinde tutulmaz; yalnız tek yönlü doğrulama materyali saklanır.
- Yanlış hesap, yanlış tenant, süre aşımı, revoke ve replay fail-closed reddedilir.
- Owner/manager/staff ve mali izin matrisi server-side uygulanır.
- Staff kendine veya başkasına manager/owner ya da mali izin veremez.
- Manager owner gibi mali izin dağıtamaz.
- Pasifleştirme ve rol düşürme sonraki istekte güncel DB membership üzerinden etkili olur.
- StaffProfile ile login Membership aynı nesne sayılmaz; bağlantı isteğe bağlı ve tenant-bounded'dır.
- Genel amaçlı policy engine, service-role backend veya yeni üst tenant/şube modeli kurulmaz.
