## Stabilization sözleşmesi

`docs/plan/stabilization.md#s08` bulgusu mevcut tenant izolasyonunun bozuk olduğunu iddia etmez. Açık, gelecekte `public` gibi exposed schema içinde `postgres` migration rolüyle yaratılan yeni **table/view, sequence ve function** nesnelerinin varsayılan object ACL'lerini fail-closed doğrulayan kapının eksik olmasıdır.

S08 ile RLS ve object privilege iki ayrı katman olarak korunur:

- Yeni table/view ve sequence, `anon` veya `authenticated` için otomatik object privilege kazanmaz.
- Yeni function, PostgreSQL'in `PUBLIC EXECUTE` varsayılanı ve hosted Supabase'in schema-scoped API-role varsayılanı açısından kapalı kalır.
- Erişim ancak bilinçli `GRANT` ile açılır; table/view satır erişiminde ayrıca uygun RLS policy gerekir.
- `SECURITY DEFINER` probe açık API yüzeyi yapılmaz.
- F17-01'in açıkça grant edilmiş authenticated operator RPC'leri, dar anon management/public-booking RPC'leri ve server-secret-gated notification dispatch yüzeyi regresyon testinde yeniden kontrol edilir.

K01–K03 ve mevcut router davranışı değişmez. Birleştirilmiş migration dosyaları değiştirilmez; yalnız ileri S08 migration eklenir.

## Uygulama

### İleri migration

`supabase/migrations/20260913201500_s08_db_object_access_gate.sql`

`postgres` rolünün `public` schema geleceği için:

- tables üzerindeki `anon, authenticated` default privileges kaldırılır; PostgreSQL `ON TABLES` kapsamı view'ları da içerir,
- sequences üzerindeki `anon, authenticated` default privileges kaldırılır,
- functions için hem global `PUBLIC EXECUTE` hem schema-scoped `anon, authenticated EXECUTE` default'u kapatılır.

Migration mevcut nesnelerin ACL'sini yeniden yazmaz; yalnız sonradan oluşturulacak nesnelerin varsayılanını değiştirir. Böylece S08 mevcut çalışan explicit grant yüzeyini daraltmaz. `service_role` varsayılanları bu dar S08 kabulünde değiştirilmez; görev kartının anon/authenticated erişim kapısı ve mevcut F17 çalışma yüzeyi korunur.

### Disposable negatif / pozitif erişim testi

`supabase/tests/s08_db_object_access_gate.sql`

Test, vanilla PostgreSQL'in doğal kapalı table/sequence varsayılanından yanlış yeşil almamak için önce eski hosted proje davranışını yeniden kurar:

1. `postgres/public` default ACL'lerinde table için select/insert/update/delete, sequence için usage/select yeniden `anon, authenticated` rollerine verilir.
2. Gerçek S08 migration dosyası `\ir ../migrations/20260913201500_s08_db_object_access_gate.sql` ile yeniden uygulanır.
3. Gerçek ürün tenant/rol modeli için iki Business ve owner/manager-sınırında kullanılacak owner/staff Membership fixture'ları transaction içinde kurulur.
4. Disposable table + identity sequence + `security_invoker` view + invoker function + `SECURITY DEFINER` function yaratılır.
5. Explicit grant öncesi hem `anon` hem `authenticated` için table/view/sequence/function yetkileri negatif doğrulanır.
6. Yalnız authenticated probe yüzeyine explicit table/sequence/view/invoker grant verilir; definer kapalı kalır.
7. Tenant A owner hesabı kendi Business satırlarını okur/yazar; tenant B satırı görünmez ve tenant B'ye INSERT RLS tarafından reddedilir. Owner/BYPASSRLS bu kabulde kullanılmaz.
8. Tenant A staff hesabı aktif üyelik nedeniyle kendi tenant satırlarını okuyabilir, fakat `can_manage_business()` kullanan INSERT policy'sini geçemez. Böylece tenant ve uygulama rolü ayrı negatif kanıtlanır.
9. `security_invoker` view aynı tenant RLS sınırını korur; explicit invoker function ve sequence pozitif çalışır.
10. `anon` table, view, sequence, invoker ve definer erişimlerinin tümünde object-grant katmanında negatif kalır.
11. Disposable nesneler ve tenant fixture'ları transaction sonunda `ROLLBACK` ile temizlenir.

## Local ve hosted migration rolü farkı

Yerel CI bootstrap, hosted Supabase'in function default grant davranışını zaten modelliyor. Vanilla PostgreSQL table/sequence için aynı permissive Supabase proje varsayılanını kendiliğinden üretmediğinden S08 testi yalnız kendi disposable geleceği için eski hosted table/sequence default ACL'lerini geri kurar ve gerçek migration'ı yeniden uygular. Böylece eski nesnelerin ACL'si değiştirilmeden hosted migration rolü (`postgres`) davranışı test edilir.

Supabase'in yeni proje davranışı 2026'da object exposure'ı opt-in yöne taşısa da eski projelerdeki default ACL'ler migration rolü üzerinde kalabilir. Bu migration bu projeyi platform varsayımına bağlı bırakmadan açıkça deny-by-default yapar.

### Hosted staging salt-okunur envanter kanıtı

`randevu-staging` projesinde bu oturumda yalnız metadata sorguları çalıştırıldı; DDL veya veri yazımı yapılmadı.

- Bağlantı `current_user = postgres`, `session_user = postgres`: migration default ACL hedef rolü canlı ortamla eşleşiyor.
- `pg_default_acl`, `postgres/public` için future **table** varsayılanında `anon`, `authenticated` ve `service_role` rollerine tüm table ayrıcalıklarının; future **sequence** varsayılanında üç role `rwU` yetkilerinin hâlâ bulunduğunu gösterdi.
- Function tarafında F17 hardening görünür: global default yalnız `postgres=X`; `public` schema function default'unda `anon/authenticated` yok, `service_role` explicit EXECUTE kalıyor.
- `public` içinde 23 normal tablo var ve 23/23'ünde RLS + FORCE RLS açık. `anon` SELECT grant sayısı 0; `authenticated` SELECT grant sayısı 13. Bu bulgu S08'i mevcut tenant izolasyonu arızası olarak genişletmemek gerektiğini destekliyor.
- `public` içinde şu anda sequence yok; sequence riski tamamen gelecekteki migration nesnesi kapısıdır.
- `public` içindeki uygulama tarafı `postgres`-owned function sayısı 68; bunların 7'si anon, 18'i authenticated için explicit executable ve 63'ü SECURITY DEFINER. F17 regression testi bu dar açık RPC yüzeyinin S08 sonrasında aynı kalmasını doğrular.

Bu hosted envanter S08 migration'ın mevcut object ACL'lerini topluca değiştirmemesi, yalnız **future default privileges** üzerinde çalışması kararını doğrular.
