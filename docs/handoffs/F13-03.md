## Frozen scope

F13-03 consumes the accepted booking/group/customer/availability authorities rather than starting a second booking engine.

1. Operator create order is **Time → Customer → ordered service/staff lines → Note → Create**.
2. One or many service lines use the same server group planner/create transaction.
3. Create carries one idempotency key for the whole group; collision/partial-write authority remains server-side.
4. A guarded close-time action sits next to booking creation and uses the existing availability-block API.
5. Existing group/line reschedule and cancellation remain the movement/cancellation authority.
6. Native group lifecycle adds one atomic CAS/idempotent status RPC for `scheduled → confirmed → completed|no_show`.
7. Partial/cancelled/native groups are not flattened into a false terminal status.
8. Detail exposes customer/time/note/service lines and supported actions.
9. Future **Fotoğraf** and **Adisyon** connection points remain visible but disabled/informational until F16-03/F14.
10. Repeat/SMS remain explicit F16-01/F16-02 future hints, not fake controls.

## Existing authorities reused

- group plan: `POST /api/availability/group-slots`
- group create: `POST /api/bookings/groups`
- group move: `POST /api/bookings/groups/:groupId/reschedule`
- group cancel: `POST /api/bookings/groups/:groupId/cancel`
- line service/schedule/cancel: existing F11-03 endpoints
- close time: `POST /api/availability/blocks`
- legacy lifecycle: existing `/api/bookings/:id/status`

No new customer identity binding is cached in the editor. Create submits the typed contact snapshot through the accepted server customer/dedup authority, so switching text cannot silently retain another customer history id.

## Native lifecycle forward migration

`supabase/migrations/20260921023000_f13_group_lifecycle.sql`

Adds exact authenticated-only:
`set_appointment_group_status(uuid,uuid,text,integer,text)`

Contract:
- standard session + active membership;
- native groups only;
- exact optimistic `expectedVersion`;
- one `group_status` booking command idempotency claim;
- transitions only `scheduled → confirmed`, then `confirmed → completed|no_show`;
- all physical lines update in one transaction under the existing F11 batch/management guard;
- group header receives one final status + one version bump;
- one immutable appointment event per physical line with the same final group version;
- nonuniform/partial group fails closed;
- stale version fails closed;
- replay of the same command reads the already-committed group instead of mutating again.
