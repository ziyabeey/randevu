## Delivered boundary

F14-02 introduces the server-authoritative ticket/adisyon model without pulling F14-03 payment events or F14-04 UI forward.

### Ticket root

`public.tickets` owns:

- one immutable business/customer/source identity;
- optional booking-group source;
- `open | closed | cancelled` lifecycle;
- optimistic `version`;
- one currency per ticket once the first service line exists;
- customer identity snapshots;
- actor/time metadata for creation, close and cancel.

A booking group may have at most one ticket. Walk-in tickets have no booking-group source.

Ticket deletion is forbidden. Financial history is not removed through business cascade.

### Service lines

`public.ticket_lines` currently accepts only `source_type = service`.

Each line preserves:

- source appointment-line identity when created from a booking group;
- service and optional staff identity;
- service/staff name snapshot;
- catalog price type, min/max, currency and policy version;
- exact finalized unit price;
- discount amount;
- actor/time/reason evidence for finalization and discount.

Appointment-derived service lines are copied from the accepted immutable F11 appointment snapshots, not re-priced from the current catalog.

Fixed-price sources are finalized automatically from the authoritative snapshot.

Range-price sources remain `settlementReady=false` until an explicit exact price is recorded. Finalizing a range price always records actor/time/reason; an outside-range exact amount therefore cannot be silent.

A line's immutable source/snapshot identity cannot be rewritten. Closed/cancelled ticket lines cannot be changed.

Products/packages remain F15/F16 scope.

## Financial authority

F14-02 reuses F10-02 financial permissions.

- owner and manager receive the existing effective permission behavior;
- staff require an explicit owner-managed grant;
- every ticket mutation checks `pricing_adjustments_write` at the HTTP boundary;
- every guarded RPC checks the same current permission again in PostgreSQL;
- revoking a staff grant blocks its next write;
- F14-02 does not consume `payments_write`.

No second permission system exists.

## Money contract

All amounts are integer minor units.

There is no client-side financial truth source.

Ticket projection exposes:

- `estimateMinMinor`
- `estimateMaxMinor`
- `settlementReady`
- `subtotalMinor`
- `discountMinor`
- `totalMinor`
- `paymentStatus`
- `paidMinor`
- `balanceMinor`

F14-02 has no payment-event table by design, so accepted F14-02 projections remain `paymentStatus=unpaid` and `paidMinor=0`. F14-03 replaces that static payment projection with append-only payment/refund/correction events.

A ticket cannot close with zero lines or an unresolved range-priced service.

Discount is integer minor-unit and cannot exceed the exact service amount.

## Idempotency and command history

`public.ticket_commands` scopes a command by:

`business + actor membership + command + idempotency key + request hash`.

Same key and same hash replays the stored result.

Same key and different hash conflicts.

The result-finalization update is the only allowed update to a command row. After that, command identity/result is immutable and deletion is forbidden.

This command history preserves mutation actor, command, request binding and resulting ticket projection without creating a general accounting ledger.

## Booking-group concurrency

`open_ticket_from_booking_group_guarded` serializes on a business+booking-group advisory key.

Different valid idempotency keys racing for the same booking group converge to the same ticket ID.

The unique partial index on `(business_id, appointment_group_id)` is the final duplicate guard.

The real dblink acceptance proves two concurrent writers return one durable ticket while retaining both command receipts.

## HTTP routes

Read:
- `GET /api/tickets/:id`

Mutations:
- `POST /api/tickets/from-booking-group`
- `POST /api/tickets`
- `POST /api/tickets/:id/service-lines`
- `POST /api/tickets/:id/lines/:lineId/finalize-price`
- `PUT /api/tickets/:id/lines/:lineId/discount`
- `POST /api/tickets/:id/close`
- `POST /api/tickets/:id/cancel`

The selected business is always derived from verified workspace membership. Client-supplied business IDs are not authority.

Unsafe routes remain under the shared Origin/CSRF mutation guard.

## Persistence / ACL

New raw tables are not granted to `anon` or `authenticated`.

Authenticated access is through bounded RPCs and the ticket read projection.

Composite tenant FKs bind ticket/customer/group/line/service/staff/membership identities to the same business.

RLS is enabled and forced on ticket roots/lines/commands.

## F14-03 handoff

F14-03 owns:

- manual cash/card payment event;
- partial/split payment;
- correction and refund event types;
- source-payment refund reference;
- balance calculation from append-only financial events;
- overpayment/over-refund rejection;
- payment idempotency and payment concurrency;
- payment permission via `payments_write`;
- reopen/correction policy after a financial event exists.

F14-03 must not mutate or replace F14-02 source snapshots or finalized command receipts.

## F14-04 handoff

F14-04 consumes these server projections for ticket list/editor/payment UI.

The client displays server totals and lifecycle/payment status; it does not compute authoritative totals or mark a network-ambiguous write as completed locally.
