## Interrupted media lifecycle forward repair

Forward migration: `20260914110600_f12_media_lifecycle_repair.sql`.

Problem: Worker begin → Storage → finalize/finish zincirinin ortasında process/request ölürse `pending` veya `deleting` metadata kalabilir. Base migrationın kanonik kimliği değiştirilmeden forward repair uygulanır.

Repair sözleşmesi:
- `list_business_public_media_cleanup(uuid)` artık guarded, **volatile** bounded reclaim çağrısıdır,
- fresh `pending/deleting` satırlara **15 dakika grace** verilir,
- grace'i aşan `pending/deleting` satırlar `cleanup` durumuna geçirilir,
- explicit `cleanup` satırlar beklemeden cleanup adayıdır,
- tek çağrı en fazla **20** adayı deterministik `updated_at,id` sırasıyla döndürür,
- begin/finalize/delete/restore/finish/reclaim aynı business row `FOR UPDATE` lifecycle lock'ını kullanır,
- Storage DELETE `404` terminal başarı kabul edilir,
- `finish_business_public_media_delete()` tekrar çağrıldığında metadata zaten yoksa idempotent `true`, kendi business'ında non-terminal satır varsa `false` döner,
- reclaim başka business'ın object path'ini listeleyemez veya silemez,
- stale orphan'lar Storage tekrar erişilebilir olduğunda cleanup edilerek 20-media quota'yı kalıcı kilitlemez.

Delete semantics: normal request içindeki Storage failure mevcut restore yoluyla `ready`/cover durumunu geri yükler. Gerçek interruption grace'i aştığında cleanup kazanırsa delete intent terminal kabul edilir ve cover geri diriltilmez.
