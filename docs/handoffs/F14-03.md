## Delivered boundary

F14-03 adds the append-only manual money-event layer on top of the accepted F14-02 ticket model.

Event types:

- `payment`
- `correction`
- `refund`

Manual payment methods are `cash | card`.

No provider payment, invoice engine, accounting ledger, product/package/promotion/commission model or F14-04 UI is introduced.

## Authority

F14-03 reuses the existing F10-02 financial permission model.

Every payment/refund/correction write requires current `payments_write`:

- HTTP checks the verified workspace membership and effective permission;
- guarded PostgreSQL RPCs independently re-derive the actor and re-check the same permission;
- owner/manager keep the existing effective permission behavior;
- staff require an explicit owner-managed grant;
- revocation blocks the next write.

No second payment permission model exists.

## Append-only event model

`public.ticket_payment_events` is raw financial history.

Each event preserves:

- business + ticket identity;
- event type;
- source payment when applicable;
- manual method;
- correction direction when applicable;
- integer minor-unit amount;
- mandatory reason for correction/refund;
- actor membership;
- server timestamp.

Corrections/refunds reference an original payment from the same business and ticket.

The raw table is not granted to `anon` or `authenticated`. API consumers receive the bounded ticket projection instead.

Payment events cannot be updated or deleted, including by privileged accidental writes through normal table DML. Business deletion does not cascade through the payment ledger.

## Money projection

Ticket projection now derives:

`net paid = payments + correction increases - correction decreases - refunds`

and:

`balance = ticket total - net paid`

Server projection exposes:

- `paymentStatus = unpaid | partial | paid`
- `paidMinor`
- `balanceMinor`
- ordered payment event history

All amounts are integer minor units.

The projection fails closed if net paid becomes negative or exceeds the finalized ticket total.

## Source-bound correction / refund

Correction/refund source must be an original `payment` event on the same ticket.

Source contribution is derived from the original payment plus its correction/refund descendants.

A decrease/refund may not drive that source contribution below zero.

Correction increase may not create overall ticket overpayment.

Same command key + same request hash replays the stored result; same key + different payload conflicts through the accepted F14 ticket-command authority.

## Ticket lifecycle interaction

Service/ticket lifecycle remains separate from payment lifecycle.

- payment requires a settlement-ready ticket;
- cancelled tickets reject new payment;
- ticket close requires zero balance;
- closed ticket source/service history remains immutable;
- refund/correction and later re-settlement may occur append-only after close without reopening the ticket;
- ticket cancellation creates no automatic refund.

After the first financial event:

- new service-line insertion is DB-blocked;
- discount changes may not push ticket total below current net paid.

## Concurrency

All payment/refund/correction/close paths serialize through the ticket root lock before financial decisions.

The real dblink payment race proves that two concurrent 400 TL-equivalent writes against a 600 TL-equivalent ticket cannot both succeed:

- one writer commits;
- one writer fails with overpayment;
- durable balance stays nonnegative and bounded;
- the ticket can subsequently settle exactly.

## HTTP routes

F14-03 adds bounded mutation routes under the existing cookie/Origin/CSRF guard:

- `POST /api/tickets/:id/payments`
- `POST /api/tickets/:id/corrections`
- `POST /api/tickets/:id/refunds`

Business identity is derived server-side from verified membership; client-supplied tenant identity is not authority.

## F14-04 handoff

F14-04 may build ticket/payment UI on these projections and routes.

The client must:

- display server-returned totals/status;
- generate stable idempotency keys for retryable writes;
- treat ambiguous network outcomes as unknown until same-key replay resolves them;
- never compute authoritative paid/balance state locally;
- never bypass `payments_write` based on UI visibility.

F14-04 does not get permission to rewrite payment events or ticket source snapshots.
