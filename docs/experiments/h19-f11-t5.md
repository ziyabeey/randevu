# H19 / F11 T5 benchmark preregistration

Status: experimental, non-production, test-only.

Base snapshot: `main@9c9d8b510feed03e0a84e4a74309e80954bd2810`.

## Frozen six axes

- D0 — authorization / tenant
- D1 — atomicity / idempotency
- D2 — snapshot / price / policy
- D3 — staff / capacity
- D4 — time / buffer / boundary
- D5 — concurrency / version

Axis order is frozen from request lifecycle semantics, not selected after coverage results.

## Frozen 19-row H19 suite

The suite is:

- 1 clean center;
- 6 exact single-fault rows;
- 12 exact double-fault rows at cyclic distance 1 or 2 on the six-axis ring.

The three antipodal distance-3 pairs are holdouts:

- D0 × D3 — authorization × staff/capacity
- D1 × D4 — idempotency × time/boundary
- D2 × D5 — snapshot × concurrency

No result may move a holdout into the H19 suite retroactively.

## What this benchmark is allowed to claim

The frozen H19 suite is a controlled low-order fault geometry, not a generic covering array.

Exact interaction-assignment coverage for the 19 rows:

| strength | covered | total | coverage |
| ---: | ---: | ---: | ---: |
| 1 | 12 | 12 | 100% |
| 2 | 57 | 60 | 95% |
| 3 | 128 | 160 | 80% |
| 4 | 147 | 240 | 61.25% |

A deterministic 19-row combinatorial baseline reaches 60/60 pairwise, 160/160 three-way, and 221/240 four-way assignment coverage. H19 therefore must not be described as a pairwise replacement.

The intended candidate advantage is explainable, isolated fault injection:

- all 6 exact single faults are present;
- 12 of 15 exact double-fault supports are present;
- the 3 antipodal supports remain blind holdouts.

## Runtime mutation phase

Runtime mutation kill-rate is not claimed by this file.

The next phase must run real mutants against the disposable PostgreSQL test chain.
The first calibration mutant is the D2 × D5 holdout: weaken the final service
snapshot mismatch fence and confirm that the dedicated price-race proof kills it.

Three preregistered H19 interaction gaps remain candidates for dedicated runtime probes:

- D2 × D3 — snapshot/policy × staff/capacity coherence;
- D1 × D3 — replay/idempotency × changed staff authority;
- D2 × D4 — snapshot/policy × temporal boundary coherence.

These labels are frozen before runtime results.


## T5 runtime results

These results were recorded after the frozen matrix and mutation expectations above.

### D2 × D3 coherence race

Exact head: `131a699cb542b2b7b090909f49811f91ed45211b`

Canonical CI: #2098 / run `35751809273`, job `106827903198` — SUCCESS.

The creator first observed the old service price and deterministic staff A. A concurrent
authenticated catalog transaction then repriced the service and disabled staff A's
assignment before the creator crossed the remaining schedule-authority barrier. The
creator replanned and committed staff B with the current financial/policy state.

Receipt:

`H19 T5 D2xD3 PASS: stale price/staff plan replanned coherently to new price + backup staff`

Verdict: **PASS / coherence proof**. This did not discover a production bug; it proved
that the H19-selected cross-authority interaction is already handled by the current
F11 lock/replan/final-fence design.

### Current interpretation

The calibration supports the narrow claim that the frozen H19 geometry is useful as
an explainable low-order fault taxonomy:

- two preregistered H19-covered interaction mutants were killed by their mapped
  existing proofs;
- the preregistered antipodal holdout was killed by an external control, and is
  not retroactively credited to H19;
- the new D2 × D3 runtime probe selected by H19 exercised a real cross-authority
  race and passed coherently.

It does **not** show that H19 beats pairwise/combinatorial generation on generic
coverage, nor that H19 discovered a new production defect.


### Scenario-level holdout calibration

A separate D1 × D4 holdout mutant omitted `startsAt` from the group-create
idempotency request hash. CI #2102 / run `35754568658` was killed by the
changed-start scenario inside `f11_group_create_atomicity.sql`.

This does **not** count as H19 coverage because D1 × D4 is one of the frozen
antipodal holdouts. The result demonstrates that file-level attribution is too
coarse: one SQL file can contain both H19-covered and holdout scenarios.
H19 accounting therefore stays scenario-level.

### M3 differential incremental-coverage experiment

Mutation M3 removed the second post-lock `f11_plan_group_at(...)` call from
`f11_create_group_internal`. The creator therefore reused its stale
pre-authority-lock plan.

This was evaluated as a preregistered A/B experiment:

| arm | executable coverage | result |
| --- | --- | --- |
| CONTROL | current production suite only | **PASS** |
| H19 | same mutant + H19 D2 × D3 coherence probe | **FAIL / KILLED** |

CONTROL exact head `38e4b0829e6691de12c110cf428dc6bbb50716aa`:
CI #2106 / run `35758094801` succeeded. The existing schedule-authority race
proofs passed and the PostgreSQL plan completed 308 steps.

H19 exact head `4366754661338304aa709e0d8416b62f3e82b8b2`:
CI #2107 / run `35758101561` failed in
`h19_f11_snapshot_staff_coherence.sql` with
`SERVICE_PRICE_SNAPSHOT_MISMATCH`.

The failure mechanism is informative. Without the post-lock replan, the creator
kept the old price/staff plan. The final financial fence prevented an invalid
commit, so safety remained fail-closed; however, a valid backup staff/current
price state existed and the creator no longer made forward progress to it.

Verdict: **incremental H19 coverage demonstrated for this mutant**.

The narrow supported claim is now stronger than taxonomy alone: the H19-selected
D2 × D3 scenario detected one coherent-success/liveness regression that the
existing suite accepted. This still does not imply better generic combinatorial
coverage than pairwise/covering-array methods.
